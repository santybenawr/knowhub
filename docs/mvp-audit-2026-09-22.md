# KnowHub · Auditoría y preparación del MVP

Fecha: 22 de septiembre de 2026. Rama de aplicación: `codex/knowhub-production-readiness`.

## Objetivo y alcance

Preparar una demostración local en aproximadamente una semana y media, con publicación posterior deseable. Revisión de rutas, autenticación, permisos, almacenamiento, documentos/notas/reuniones, recuperación de conocimiento, colas, configuración, dependencias y pruebas. Es una revisión de riesgos y flujos críticos; no una certificación de ausencia de errores ni una auditoría exhaustiva de cada línea.

La aplicación es Next.js con servicios TypeScript, Drizzle y PostgreSQL/PGlite. La landing y la presentación de campañas son entregables distintos. No se despliega el backend sobre la rama de marketing.

## Pendientes que condicionan una beta pública

Prioridad alta antes de usar datos reales:

1. **Base remota y TLS**: `src/server/db/client.ts` acepta certificados sin verificarlos; la migración RLS depende de `auth.uid()` de Supabase y necesita pruebas con roles y autenticación reales. Validar configuración, migraciones, aislamiento y restauración en staging.
2. **Procesamiento durable**: `src/server/jobs/index.ts` usa trabajo en proceso. La deduplicación consulta antes de insertar; un intento que agota su límite y cuyo proceso muere puede permanecer en `processing`. Probar reinicios y procesamiento concurrente, y definir un worker supervisado. El drenado tras fallo transitorio se corrige en esta revisión.
3. **Ediciones durante indexación**: cambios mientras un job ya está activo y reemplazos de audio durante el pipeline requieren control de versión del recurso. Una lectura posterior a un guardado debe usar el contenido actual.
4. **Cuentas**: transporte de correo, verificación de email, recuperación real y carrera entre login/reset pendientes. No hay eliminación/exportación completa de cuenta ni política técnica de retención implementada.
5. **Proveedores**: no se ha probado aquí IA o transcripción con credenciales reales. Usar corpus en español y comparar citas, participantes, decisiones y pendientes contra la fuente. No presentar salida mock como transcripción de una grabación.
6. **Grabación**: validar micrófono, permisos, suspensión, interrupciones, red inestable y recuperación del audio en Safari/iPhone. La captura actual conserva chunks en memoria; revisar liberación de pistas y recuperación tras fallo de subida.
7. **Cuotas/pagos**: conteo de almacenamiento incompleto (documentos frente a audio), consumo no reservado atómicamente, ausencia de checkout/webhooks/entitlements. Los planes personales y de equipo requieren precios y reglas acordados, luego sandbox de pagos. App Store/StoreKit y Apple Developer son otra fase.
8. **Entrega web**: validar CSP con audio de almacenamiento remoto, accesibilidad, rendimiento, iconos PWA y observabilidad. Configurar secretos y backups sin incluirlos en Git.

Mantenimiento adicional: `db:generate` no tiene un archivo de configuración Drizzle y falla actualmente. La app aplica sus propias migraciones TypeScript; hay que acordar cómo integrar la generación antes de usar ese comando para evolucionar el esquema. La exportación explícita de SQL sí se comprobó, sin ejecutar cambios contra una base de datos.

## Preparación y guion de la demo local

Desde la carpeta de la app:

```sh
pnpm install --frozen-lockfile
npm run demo:prepare
npm run demo
```

Abrir `http://127.0.0.1:3010/login`. Usuario de demostración: `demo@knowhub.test`; contraseña pública de datos ficticios: `knowhub-demo-2026`.

`demo:prepare` compila con Webpack y ejecuta el seed idempotente. El perfil usa `.data/presentation/database`, `.data/presentation/storage` y un secreto local aleatorio excluido de Git. No borra datos existentes. `npm run demo` escucha exclusivamente en el equipo local; no es una publicación accesible por Internet. No ejecutar otra instancia sobre la misma base PGlite.

Secuencia de presentación:

1. Iniciar sesión y explicar workspace/proyecto.
2. Crear una nota, esperar «Guardado», recargar y comprobar el contenido.
3. Subir un documento Markdown, esperar procesamiento y abrir texto extraído.
4. Importar una transcripción con nombres y tiempos; abrir transcripción, decisiones y pendientes.
5. Buscar un término concreto y hacer una pregunta sobre una decisión documentada.
6. Abrir la fuente citada y contrastarla con el texto original.
7. Preguntar por información ausente y mostrar la abstención.
8. Explicar qué usa proveedores de ejemplo y qué integra servicios reales en la siguiente fase.

Los datos semilla son ficticios. Para una demostración de transcripción real hace falta un proveedor conectado y validado, o importar una transcripción preparada y revisada por el equipo.

## Validación

La línea base pasó lint, TypeScript y 168 pruebas. Se reprodujeron seis regresiones antes de corregirlas. Resultados de esta revisión:

| Comprobación | Resultado |
| --- | --- |
| `npm run lint` | Sin errores |
| `npm run typecheck` | Sin errores |
| `npm test` | 206 pruebas en 25 archivos aprobadas |
| `npm run test:e2e` | 8 recorridos Chromium aprobados; datos y proveedores de prueba |
| `npm run demo:prepare` | Compilación Webpack y preparación de datos locales completadas |
| `pnpm audit --prod --json` | 0 avisos reportados en dependencias de producción |
| `pnpm audit --json` | 0 avisos reportados incluyendo desarrollo y dependencias opcionales (658 entradas) |
| Drizzle export antes/después del parche esbuild | SQL idéntico; no se modificó ninguna base de datos |
| `git diff --check` | Sin errores de espacios |

Los E2E verifican registro/onboarding, nota/búsqueda/cita, documento y texto extraído, audio de prueba con transcripción mock, importación de transcripción, aislamiento de reunión entre cuentas, guardado lento sin duplicación y errores de streaming. El guardado lento detectó una reconstrucción del editor con contenido anterior al cambiar la URL antes de finalizar los guardados; se corrigió y se repitió el recorrido.

El primer intento Chromium fue bloqueado por el sandbox de macOS antes de ejecutar los casos. La ejecución con permisos adecuados pasó; no se eliminaron pruebas para ocultar ese fallo. La auditoría de paquetes describe los avisos conocidos por el registro en esta fecha; no certifica seguridad del código propio ni de una instalación futura.

También se comprobó manualmente el inicio de sesión y dashboard de la cuenta semilla, la pregunta de ejemplo y el enlace a la reunión. Preparar la demo por segunda vez conserva la cuenta existente. Detenerla con Ctrl+C termina sin una traza de error; el secreto y los datos sobreviven al reinicio.

## Secuencia hasta la sustentación

- Días 1–2: cerrar regresiones y ensayo completo local; registrar límites y congelar el guion.
- Días 3–4: corpus real en español, pruebas de audio en los dispositivos del equipo y proveedor real si se dispone de cuenta/credenciales.
- Días 5–6: staging público opcional, únicamente después de cerrar sus bloqueos de aislamiento, persistencia y procesamiento.
- Días 7–8: ensayo de los cinco integrantes, errores/red desconectada y respaldo local.
- Días 9–10: congelar versión, último ensayo y preparar evidencia de pruebas para el jurado.

Las fechas son una propuesta relativa al plazo comunicado; publicación y pagos no son criterios que esta revisión declare cerrados.
